# Voicedrive V0 架构

> 面向司机的**语音群消息**应用：对设备说话，消息自动发到群里。
> 没有对讲按钮，没有实时语音流，也没有 RTC。

---

## 1. 一句话与关键约束

用户对设备说"给夜班组说一句我快到收费站了"，灵矽理解后调用我们的云端 MCP，我们把这条消息推给群里其他人。

**约束**：灵矽不会把用户音频转交给我们，`tools/call` 的参数只有文本。

**但音频并没有消失**——它在设备上。设备采集 PCM 后同时喂两路：

```
麦克风 ─┬─→ 灵矽（16k PCM 上行）→ ASR → 文本 → tools/call
        └─→ 我们自己（同一份 PCM）→ 消息音频 → 其他设备播放
```

所以群里听到的是**本人原声**，不是合成音。TTS 只在"没有音频"的时候兜底，比如 CI 里的文本注入（§4）。

这条路径已实测通过：`linx-emu -wav` 把一段 WAV 当麦克风上行，灵矽 ASR 正确识别并触发了 `tools/call`（见附录）。上行用裸 PCM 即可，不需要 Opus。

---

## 2. 四个不做

| 不做 | 原因 |
| --- | --- |
| **不做 PTT 按钮** | 语音是唯一入口。用户怎么说话、什么时候说话，由灵矽的唤醒词/自由对话决定，不是我们 |
| **不做实时对讲（RTC/SFU）** | ① 消息形态能覆盖司机场景；② 不需要上行实时流到我们；③ 省掉一整套媒体面 |
| **不做多方混音/抢占** | 消息天然是"排队播放"，不存在谁抢麦 |
| **不做真机** | **最终成品就是电脑上的模拟设备**。不画板、不烧固件、不做 OTA、不做功耗。跑起来就是一个可执行文件 × N |

代价：一条消息 3~5 秒才响（见 §4 实测）。换来的是服务数从 9 个变成 1 个，硬件从一台样机变成 `go run`。

## 3. 架构

```
  麦克风/文本 ────▶ │        灵矽 AI 平台          │
                     │  ASR · LLM · TTS · 云端MCP   │
                     └──────┬───────────────┬──────┘
                   音频上行  │               │ tools/call（文本）
                     ┌──────┴──────┐        ▼
                     │  模拟设备     │  ┌──────────────────────────┐
                     │  linx-emu    │  │  voicedrive 服务（1 个）  │
                     │ （可多开）    │  │  · 群 / 成员             │
                     └──┬───────┬──┘  │  · 消息与投递            │
                    控制面 WS │  原声上传 │  · MCP Server（云端）     │
                        └───────┴───▶│  · 音频（不合成，直接用）  │
                                      └────────┬─────────────────┘
                                      音频写入  │  ▲ 设备拉流
                                      ┌────────▼──┴──────────────┐
                                      │ 对象存储 / 本地目录        │
                                      └──────────────────────────┘
```

模拟设备 = 一个 Go 程序，一条命令起一份，带自己的 MAC。三个窗口 = 三个人在群里。

**同一份 PCM 喂两路**：一路给灵矽做 ASR，一路留给自己，成为群消息的原声。

三条链路，各自职责清楚：

| 链路 | 谁连谁 | 承载 |
| --- | --- | --- |
| 语音 | 模拟设备 ⇄ 灵矽 | 麦克风 PCM 上行（或用 `listen.detect{text}` 注入），听 TTS 回来 |
| 工具 | 灵矽 → 我们 | `tools/call`：建群、发消息、切群 |
| 控制 | 我们 ⇄ 模拟设备 | 消息通知、状态上报、播放控制 |

**语音链路是灵矽独占的；我们只经手文本和音频文件。**

## 4. 发送链路（核心）

```
用户： "给夜班组说一句，我快到收费站了"
  │
  ▼ ① 设备采集 PCM，同一份同时走两路
      ├─→ 灵矽：16k PCM 上行 → ASR → "给夜班组说一句我快到收费站了"
      └─→ 本地：留在环形缓冲里，等消息落库后上传
  │
  ▼ ② LLM 决定调用工具
tools/call  group.send_voice
            {"group":"夜班组", "text":"我快到收费站了"}
  │
  ▼ ③ 我们：写库 → 控制面给发送方推 bind_message{id}
  │      设备据此上传刚才那段 PCM → 服务端存为消息音频
  │      （群里在线的设备同时被通知有新消息）
  ▼ ④ 返回给灵矽
content.text = "好，已发给夜班组的老王和小李"
  │
  ▼ ⑤ 灵矽 TTS 播给发送者（只有他自己听到）
```

**TTS 只在拿不到音频时兜底**：快路径是"设备上传原声"，只有文本注入（CI 测试）或上传超时（3s）时才合成一段。

**实测延迟**（真实灵矽平台，deepseek-v4-flash）：

| 环节 | 实测 |
| --- | --- |
| 说完 → `stt` | < 100ms |
| `stt` → `tools/call` 到达 | **~2s** |
| `tools/call` → 我们返回 | 待测（不依赖音频，可立即返回） |
| 返回 → `tts start` | < 500ms |

发送方体验的关键：**`group.send_voice` 立即返回**，音频在后台补上。否则用户要干等合成。

> 群名要归一化：用户说"夜班"、"夜班组"、"上夜班那个群"都得落到同一个 group。用"群别名表 + 模糊匹配 + 命中多个就反问"三步，不要交给 LLM 猜。

## 5. 接收与播放

```
消息落库 → 查群成员在线设备 → 控制面推送
  {"type":"message","id":"m_123","from":"老王","group":"夜班组",
   "audio_url":"https://cdn/.../m_123.opus","duration_ms":3200,"seq":42}
  → 设备 HTTP 拉流边下边播 → 播完回报 {"type":"played","id":"m_123"}
```

**必须做的仲裁**（这是唯一不能省的状态机）：

| 场景 | 处理 |
| --- | --- |
| 正在放群消息，又来一条 | 排队，播完再放；连续 3 条以上只播最新一条 + "还有 N 条" |
| 正在放群消息，用户开口说话 | **本地立即静音**，再发 `abort` 给灵矽；消息插入未读 |
| 灵矽 TTS 播放中，消息到达 | 排队等 TTS 结束（`tts stop` 后播放） |
| 正在播消息，SOS 到达 | 立刻切，播 SOS |

**本地静音永远先于网络信令。** 等 `abort` 往返回来再静音，用户会听到半句被截断的 AI 语音。

## 6. 数据模型（4 张表，够用）

```sql
device(id, mac, user_name, agent_id, bound_user_id, last_seen_at, last_acked_seq)
"group"(id, name, owner_device, invite_code, ttl_at, created_at)
membership(group_id, device_id, alias, state, joined_at)   -- alias: 老王 / 小李
message(id, group_id, from_device, text, audio_url, duration_ms,
        seq, created_at)
```

- `seq`：每群单调递增，设备按 `last_acked_seq` 拉增量，天然支持离线补发
- `alias`：群里显示"老王"，而不是 MAC
- 不建 Redis：几万设备用 Postgres 的行锁 + `LISTEN/NOTIFY` 足够；真到瓶颈再加

## 7. MCP 工具（云端，5 个）

| 工具 | 参数 | 返回给灵矽读的话 |
| --- | --- | --- |
| `group.send_voice` | `group`, `text` | "好，已发给夜班组的老王和小李" |
| `group.create` | `name` | "群建好了，口令 482913" |
| `group.join` | `code` | "已加入夜班组，共 5 人" |
| `group.list` | – | "你在 3 个群：夜班组、家庭群、沪宁线" |
| `group.switch` | `group` | "现在只听夜班组的消息" |

实现要点（都是从协议文档和实测里踩出来的）：

1. **身份只认 Header** `X-Linx-Device-Id`，绝不接受模型传的 device_id。
2. **返回文本 ≤ 40 字**，超了 TTS 会念很久，司机在开车。
3. **不要依赖 `structuredContent.funcs` 扩展**，平台只保证 `linx_play` / `linx_stop` / `change_role`；设备动作走我们自己的控制面。
4. **写操作要幂等**：用户连说两遍"发一句"不应该发两条，用 `device_id + text + 30s 窗口` 去重。
5. **缺参数就反问**，不要编默认群名。

## 8. 模拟设备要做的事（很少）

模拟设备 = 一个 Go 程序，复用现有的 `cmd/linx-emu`，补四块：

```
linx-emu
├── 灵矽 WS 客户端：已有（hello / listen / abort / 收 TTS 音频帧）
├── 音频输入：电脑麦克风（ffmpeg 管道）或 WAV 文件 → 16k PCM 上行   ← 已有 -mic / -wav
├── 说话入口：文本注入 listen.detect{text}（-say），CI 用
├── 我们服务 WS 客户端：收 message 推送、上报 played / 心跳
├── 音频播放：TTS 下行 PCM 直接写声卡；群消息拉 URL 解码播放
└── 多开：--mac 不同即不同设备，可同机跑 N 份
```

音频输入走外部 `ffmpeg` 进程而不是 cgo，二进制保持纯 Go。
不需要：Opus 编码、抖动缓冲、AEC、功耗管理、OTA、配网——这些属于"真机"，不在这一版范围内。

**交互只剩三个键**：回车说话、`abort` 打断、`quit` 退出。

## 9. 成本

演示阶段（自己跑）：**≈ 0**。灵矽用赠送额度，对象存储用本地目录，服务跑在本机。

如果按 1 万台真机估算未来成本（仅作参考，不在本版交付）：

| 项 | 量级 | 说明 |
| --- | --- | --- |
| 灵矽 | 会话时长 × 倍率 | **主要成本**。每次交互 ~10s，20 次/天 ≈ 200s/设备/天 |
| TTS | 20 条 × 15 字 | 按字符计费，单价极低 |
| 对象存储 + CDN | 每条 ~10KB | 语音 3 秒 ≈ 7KB，可忽略 |
| 服务器 | 1 个 Go 服务 + 1 个 Postgres | 几千元/月 |

**省钱的关键**：不要常连灵矽。空闲就断开，用户说话前再连。

## 10. 已知取舍与风险

| # | 取舍/风险 | 现状 | 何时处理 |
| --- | --- | --- | --- |
| 1 | 群里播原声，需要设备把同一份 PCM 也传给我们 | **已解决**：音频在设备上，上传即可（§4） | 已实测上行可行（附录）；只剩"哪一段"的对齐 |
| 2 | "哪一段"对齐：设备不知道自己要发哪段音频 | 用 `bind_message` 触发上传最近一句 | 先用"listen start → stt 到达"的时间窗切 |
| 3 | 发送延迟 3~5s（LLM 2s） | 接受 | 音频本身不增加延迟，它是并行的 |
| 4 | 每条消息都要经过灵矽 → 计费 | 接受 | 用会话时长控制，别常连 |
| 5 | 灵矽故障 = 无法发消息 | 接受 | 演示时用 `linx-mock` 兜底 |
| 6 | 群名识别不准 | 别名表兜底 | 持续调 prompt + 设备工具描述 API |
| 7 | 多实例同时出声会混在一起 | 演示时错开 1~2s | 播放前本地锁 + 演示脚本编排 |
| 8 | 纯文本注入时没有音频 | TTS 兜底 | 只影响 CI，不影响演示 |

## 11. V1 再谈（现在明确不做）

- 真机固件（ESP32 / 4G / OTA / 配网 / 功耗）
- 实时对讲 / RTC / SFU
- 位置、围栏、碰一碰、扫码入群
- 录音合规、审计、多租户
- 广播群、500 人上限、管理员强插
- 多区域部署、离线推送（APNs/FCM）

触发条件：**用户抱怨"声音不像本人"或"太慢"**，或者有人真的要把这东西装到车上。有信号再做，不靠猜。

## 12. 三人分工

边界不按代码目录划，按**"变化归谁处理"**划。

```
        ┌──────────────┐
        │   灵矽平台    │
        └──┬────────┬──┘
      工具 │        │ 语音
           ▼        ▼
   ┌───────────┐  ┌───────────┐
   │ A 云端服务 │  │ B 模拟设备 │
   └─────┬─────┘  └─────┬─────┘
         │  控制面 WS    │
         └──────◀───────┘
                │
        ┌───────▼────────┐
        │ C 平台与验收    │
        └────────────────┘
```

### A · 云端服务

**范围**：所有有状态的东西。群、成员、消息、音频文件、投递、补发、TTS。

**对外只有两个面**：给灵矽的 MCP 工具（文本进、文本出），给客户端的控制面 WS（消息帧）。

**不碰**：不知道客户端怎么播，不知道灵矽怎么理解人话。

> 群规则变了、消息发丢了、合成太慢 → 找 A。

### B · 模拟设备

**范围**：所有"终端"的东西。连灵矽、注入"我说的话"、播放音频、多开。

**不碰**：不知道"群"的存在，只知道自己收到了一个 `message` 帧；不判断该不该发，不存任何业务数据。

> 播不出声、多开打架、灵矽协议变了 → 找 B。

### C · 平台与验收

**范围**：所有"灵矽怎么理解我们"和"怎么证明它能用"的东西。智能体的 prompt、意图识别、工具描述、群名归一化规则、mock 平台、演示剧本。

**不碰**：不写服务端，不写客户端音频。

> 说"切到夜班"没反应、识别不准、演不出来 → 找 C。

### 三者的接口

| 边界 | 形态 | 谁定 |
| --- | --- | --- |
| A ↔ 灵矽 | 5 个 MCP 工具，纯文本 | A 定，C 验 |
| A ↔ B | 4 种 WS 帧 | A 定，B 实现 |
| A ↔ 存储 | 一个音频 URL | A |
| C ↔ 全部 | 用 mock 顶替灵矽，用剧本顶替人 | C |

一句话：**A 管业务真相，B 管终端表现，C 管灵矽的理解力和验收标准。** 三者之间只有文本和 URL 流过，没有共享代码。

## 附录：已实测的协议事实

来自 `cmd/linx-emu` 对真实平台的联调（2026-10）：

| 事实 | 结论 |
| --- | --- |
| `hello.features.mcp=true` 后立即收到 `initialize` + `tools/list` | 端侧 MCP 零配置可用 |
| `tools/call` 参数按 schema 原样传（`{"volume":30}` 是整数） | 参数类型安全 |
| `abort` → `tts stop{is_aborted:true}` | 打断生效，往返 < 100ms |
| 打断后同 session 可继续 `listen`，上下文保留 | 不必重连，省钱 |
| `listen.detect{text}` 等价于"用户说了这句话" | **无麦克风即可测全链路** |
| 下行音频 640 字节 / 20ms PCM | 与 hello 声明一致 |
| **裸 PCM 上行被接受**：按 20ms / 640 字节发送 WAV 语音，ASR 正确识别 | 原声链路可行，不需要 Opus 编码 |
| 电脑麦克风（ffmpeg → 16k 单声道 s16le）可直接当上行源 | 模拟设备能说真话 |
| `stt` → `tts start` ≈ 2s（deepseek-v4-flash） | 决定 §4 的延迟预算 |
| 计费按会话时长 × (1 + 模型系数 + 音色系数) | 与消息条数无关，与"连多久"有关 |

联调用 mock 平台，不消耗资源包：`go run ./cmd/linx-mock`，详见 `README.md`。
