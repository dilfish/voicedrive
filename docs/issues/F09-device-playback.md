## 背景

设备同时可能有三路声音：灵矽的 TTS、群里来的消息、本地提示音。谁先出声、谁让路，必须有个确定的规则。

## 做什么

- 播放队列：`message` 帧进入队列，按 seq 顺序播放
- 拉流播放：HTTP 边下边播（WAV/PCM）
- 仲裁规则：

| 场景 | 行为 |
| --- | --- |
| 正在放消息，又来一条 | 排队 |
| 连续 ≥ 3 条 | 只播最新一条，附"还有 N 条" |
| 正在放消息，用户按回车说话 | **本地立即静音**，再发 `abort` 给灵矽 |
| 灵矽 TTS 播放中，消息到达 | 等 `tts stop` 再播 |
| 播完 | 上报 `played{seq}` |

- 播放结束或打断时清理音频缓冲，不残留

## 不做什么

- 不做音量归一化
- 不做播放进度上报（V0 只报"播完"）
- 不做蓝牙/多声卡路由（演示用默认设备）

## 验收标准

- [ ] 连收 5 条，按序播放，不叠音、不错序
- [ ] 播放中点回车：0.3 秒内静音，消息进未读，随后正常对灵矽说话
- [ ] 灵矽 TTS 期间来的消息不打断 TTS，`tts stop` 后 1 秒内开始播
- [ ] 连续 3 条只播最后一条，并播报"还有 2 条"
- [ ] 播放中 kill 服务端，设备不崩溃，重连后能继续

## 技术要点

- 单一"当前播放者"状态机，所有音源共用一个输出句柄
- 本地静音是**先于任何网络操作**的动作，不要等 `abort` 的响应
- 拉流走 `http.Get` + `io.Reader` 流式解码，不要先下载完再播
- macOS 上用 `afplay` 或纯 Go 的 oto 输出，二选一，保持无 cgo 优先
